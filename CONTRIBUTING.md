# Как участвовать / Contributing

Спасибо за интерес к Laya Engine. Проект небольшой и прикладной: главное
требование — **изменения должны быть измерены**, а не «выглядеть правильными».

## Быстрая проверка перед PR

```bash
# Windows
build.cmd            # gofmt + vet + test + сборка bin\laya-server.exe

# Linux / macOS
./scripts/build.sh   # тот же набор проверок
```

Обязательно к зелёному результату:

| Проверка | Команда |
|---|---|
| Форматирование | `gofmt -l .` (пусто) |
| Статический анализ | `go vet ./...` |
| Быстрые тесты | `go test ./...` |
| Сборка | `go build ./cmd/laya-server` |

Тяжёлые проверки (сверка с Python-эталоном, 200 кейсов, 1200 ответов)
запускаются вручную: `LAYA_HEAVY=1 go test ./engine/ -run Reference -v` — нужны
веса и эталон. Тест сам выбирает подходящий файл эталона (`ref_answers_gpu.json`
для GPU, `ref_answers_fp16.json` для CPU) и пропускает сверку, если эталон снят на
другой модели. Почти-равные выборы (разрыв лидеров < 0.01 в эталоне) печатаются
отдельной строкой: они зависят от видеокарты, а не от кода.

## Правила, которые нельзя нарушать

Они описаны в [AGENTS.md](AGENTS.md) — прочитайте перед изменениями. Коротко:

1. Никаких загрузок из сети в рантайме сервиса.
2. Молчаливый откат CUDA→CPU запрещён.
3. Ответы модели не расширяют разрешения и не заменяют детерминированные факты.
4. Пороги — по `answer_confidence`, не по `confidence`.
5. Windows-скрипты (`.cmd`) — только ASCII и CRLF.
6. Изменения в токенизаторе/сборке входа подтверждаются сверкой с эталоном:
   любое расхождение молча меняет ответы модели.

## Что особенно приветствуется

- **Замеры, а не обещания.** Новый ускоритель/оптимизация — с числами
  (p50/p95, число токенов, воспроизводимый сценарий).
- **Платформенная поддержка**: Linux/macOS-packaging, конфигурации Docker,
  сборка без CUDA, тесты на чужих GPU.
- **Клиенты API** — примеры на других языках (сейчас есть curl, Python, Node).
- **Диагностика**: инструменты, которые сокращают время разбора сбоев.
- **Переводы** документации.

## Процесс

1. Fork → ветка с осмысленным именем (`fix/tokenizer-truncation`,
   `feat/linux-systemd`).
2. Коммиты — Conventional Commits: `fix(engine): …`, `docs: …`, `ci: …`.
3. Один PR — одно изменение; описывайте **что измерено** и как это проверить.
4. Если изменение затрагивает публичный контракт (`/decide`, схемы ответов,
   JSON-поля) — сначала issue с описанием, потом PR.

## Что не примем

- Правки ответов модели «на глаз» без сверки с эталоном.
- Тихие откаты и fallback'и, скрывающие деградацию (CPU вместо GPU, сеть при
  отсутствии файла).
- Зависимости, тянущие Python в рантайм.
- Бинарники и веса в коммитах: для них есть скрипты `scripts/fetch-*` и релизы.
